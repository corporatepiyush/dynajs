# poll_starvation_proof.txt -- captured from scratch/diag2.c (same mechanics
# as latency_harness): 15 consecutive runs of
#   let s=0; for(let k=0;k<300;k++){ s+='abcdefgh'.repeat(4194304).length; } s
# The atomic interrupt flag is set mid-eval every run ("fired at ..."), yet in
# 15/15 runs (each ~290ms of JS execution) the engine's interrupt handler is
# NEVER invoked (served=-1.000ms) and the eval completes normally (exc=0).
# Mechanism: js_poll_interrupts decrements a per-context counter initialized
# to JS_INTERRUPT_COUNTER_INIT=10000; it only calls the handler when it hits
# zero, and it is reset only at that moment. A 300-iteration loop never
# crosses the boundary; the counter persists across evals, so delivery is
# probabilistic across consecutive runs. Interrupt latency under such loops
# is unbounded (no poll at all), not merely large.
